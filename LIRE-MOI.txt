BRIDGE COMPTES — TEST D’INSERTION SAGE

1. Remplacer la source du worker comptes par BridgeWorkerAccount.cs, puis
   RECOMPILER le .exe. Modifier le .cs seul ne change pas un .exe existant.
   Ne pas compiler avec BridgeWorker.cs : ce sont deux exécutables séparés.
   Aucune modification du worker commandes n’est fournie.

2. Conserver votre config/config.accounts.json. Le worker garde les clés :
   InboxDir, ProcessingDir, DoneDir, ErrorDir, ResultsDir, LogFile,
   GcmPath, SageUser, SagePassword, PollMs.
   Utiliser des dossiers propres AUX COMPTES, distincts de ceux des commandes.
   Les chemins doivent être absolus. GcmPath doit pointer vers le dossier Sage
   de TEST : le programme écrit réellement une fiche client avec client.Write().
   La config par défaut est résolue depuis l’exécutable : ../config/config.accounts.json.

3. Exemple de compilation depuis PowerShell, si vous utilisiez le compilateur
   .NET Framework et les objets Sage 32 bits :

   & "$env:WINDIR\Microsoft.NET\Framework\v4.0.30319\csc.exe" /nologo /target:exe /platform:x86 /r:System.Web.Extensions.dll /r:Microsoft.CSharp.dll /out:BridgeWorkerAccount.exe BridgeWorkerAccount.cs

   Conserver VOTRE architecture actuelle si Sage est installé en 64 bits
   (/platform:x64 et environnement compatible). Choisir selon l’installation
   des objets métier Sage, pas selon WAMP. Reprendre votre commande habituelle
   si elle fonctionne déjà. Le code vise .NET Framework, pas .NET Core moderne.

4. Arrêter l’ancien worker comptes avant de lancer le nouvel exécutable.
   Ne lancer qu’une instance du worker comptes.

   .\BridgeWorkerAccount.exe --config "C:\CHEMIN_REEL\config\config.accounts.json"

5. Copier account_test_yazid.json dans InboxDir DES COMPTES une fois le worker
   démarré. Préparer les fichiers sous extension .tmp puis les renommer en
   .json après fin de copie pour éviter de lire un JSON incomplet.

6. Attendre le résultat dans ResultsDir : account_test_yazid_result.json.
   - success=true, created=true : fiche créée dans Sage.
   - success=true, alreadyExists=true : code déjà présent avec le même email ;
     le bridge ne modifie pas les autres coordonnées.
   - success=false : lire stage et error, ainsi que le fichier LogFile.
   L’entrée passe dans DoneDir ou ErrorDir. Les logs sont aussi affichés à l’écran.
   Un ancien résultat n’est pas écrasé : un suffixe unique est ajouté si nécessaire.

FONCTIONNEMENT
   - prénom/nom gardés séparés dans le JSON, combinés dans CT_Contact ;
   - société facultative si prénom/nom permettent de produire un intitulé B2C ;
   - longueurs contrôlées selon les colonnes SQL fournies, pas de troncature
     silencieuse, notamment pour CT_Contact et CT_Commentaire (35) ;
   - erreur d’accès COM sur un champ : remontée en erreur, pas ignorée ;
   - client existant vérifié avec ExistNumero, puis ReadNumero : une erreur
     de lecture n’est plus assimilée à un compte absent ;
   - source/platform conservées dans les résultats et logs, pas écrites dans
     des champs arbitraires de Sage ;
   - tariffCategory non appliquée, comme auparavant, mapping à définir ;
   - isNew n’est pas géré dans ce worker : c’est un état API/intégration ;
   - le suffixe tmp est conservé DANS SAGE, sans génération de CT définitif.

REPRISE APRÈS INCIDENT
   Si l’écriture du résultat ou le déplacement du fichier échoue, le worker
   s’arrête et garde le fichier dans ProcessingDir. Il peut avoir déjà écrit
   dans Sage. Vérifier logs, résultat et fiche Sage avant remise en inbox.
   Un rejeu du même code ne recrée pas la fiche si elle est déjà présente.
   Cela ne protège pas contre deux codes différents pour une même personne.
